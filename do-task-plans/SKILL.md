# 执行计划

## 验证范围

- 所有任务的日常开发和单任务验收禁止默认运行全量测试；必要的定向单元测试在本任务内完成，覆盖本次修改及直接受影响行为，优先复用现有测试，不积压到最终回归。
- 不将全量构建、全仓 lint 或格式检查作为每个子任务的固定步骤。公共检查在统一回归按需合并执行；全量测试只有用户明确要求或项目明确的统一回归流程要求时才运行，不因进入回归就自动扩大范围。
- 定向测试通过后按任务完成规则收尾；未执行或失败的检查如实记录，不宣称通过。统一回归补跨任务集成及必要公共检查，不机械重跑未受后续改动影响的已通过单元测试。
- Rust 任务另按 Rust 项目约定控制编译内存；不将 Rust 编译资源限制套用到其它语言的普通单元测试。

## 无人值守与自主决策

默认用户不在旁等待回答。执行任务本身及完成任务所需的常规、可逆、低风险操作，在已有授权范围内自主推进，不逐项请示、不重复请求已有授权，也不在完成一个步骤后询问是否继续。

- 遇到细节不明或多种可行路线时，先查阅计划、仓库约定、相关实现和工具结果，选择符合现有模式、改动小、易验证的最佳可行方案。在任务文件中简要记录影响后续执行的假设、选择和依据；`plan.md` 保持只读。
- 缺少依赖、测试失败、格式错误、命令失效或计划中的路径和符号过时时，先调查根因，自行采取范围内的依赖修复、格式化、命令调整或等效验证，并继续执行。计划步骤可据当前仓库事实作必要调整，保留原目标、验收标准和验证强度。
- 为完成原目标，可修复必要的相邻依赖并记录原因；不扩展无关功能，不覆盖他人变更，不以绕过检查、弱化断言或删除失败测试来取得通过结果。
- 对同一问题避免无证据地反复重试；依据错误结果调整方法，合理替代路径仍不可行时记录阻塞。局部受阻时继续完成不依赖它的工作，不让一个小问题阻断整个流程。
- 无人值守不扩大授权范围。未授权的破坏性操作、对外发布、不可逆变更及权限限制不能靠默认选择绕过；已有明确授权的操作不再次询问。

## 项目开发与验证入口

当前任务涉及 Rust/Cargo 构建或验证时，读取 [Rust 项目约定](references/rust.md)，按其中规则覆盖默认会话调度；Rust 验证直接使用原生 Cargo，旧任务中的包装入口改为等价原生命令并记录调整；其它任务不加载。

- 核对仓库协议、任务涉及的语言与实际可用工具。Rust 直接调用 Cargo 并复用现有缓存；其它语言沿用项目原有入口，并遵守其生命周期，不自行假定解释器、脚本或加速器存在，不为执行普通任务安装替代工具。
- Rust 使用原生 Cargo 的增量缓存运行必要定向测试，不启动额外测试运行器或兼容性探针。确认本次修改后的有效测试数及结果；零测试不算通过。其它语言使用自身既有验证工具。
- 旧任务的命令已过时但仓库提供了等价入口时，自主核对并只在对应编号任务文件记录调整，无需用户补配置；不修改只读 `plan.md`。超出工具适用边界时按项目要求重启或回到原生验证，保留最终强制检查和实机验收。
- Rust 编译取消、超时或任务收尾时，按 Rust 项目约定确认自有 Cargo/rustc 子进程已退出，再释放资源或重试；不能将工具返回或已发终止信号视为完成清理。
- 按仓库资源限制安排构建与验证，不重复初始化或清除其它任务的缓存、锁及进程；不要把当前仓库的目录、参数或并发数量推广到其它项目。

## 流程

对每个任务：
- 读取指定任务文件，再读取其引用的 `plan.md`，继承其中的公共执行、资源、验证和收尾规则；任务文件仅补充自身目标、依赖、命令、验收及专属约束。按计划引用相关仓库说明或技能。
- 按计划目标和验收标准执行；常规步骤调整按“无人值守与自主决策”处理，不因小偏差停下请求确认。
- 运行必要的定向单元测试，不跳过本任务行为验证；旧任务要求每次全量测试或整仓检查时，按“验证范围”缩小并记录调整。
- 没有新的验证证据，不要声称任务已完成或删除任务文件。
- `plan.md` 保存整体架构和公共执行规则，任何情况下都不要修改、清理或记录进度到 `plan.md`。
- 如果验证遇到问题，先调查修复并尝试适当的等效检查；仍无法运行时，只在对应任务文件中将任务保持为 `已阻塞`，记录未完成的检查和已尝试路径，不要声称成功；如果已完成实现，仅因与本次修改无关的原因无法运行验证，可以改为 `待回归`，保留任务文件供回归验证。
- 无论以 `已完成`、`待回归` 还是 `已阻塞` 结束任务，只要有本任务实际代码、测试、配置或文档变更，都必须先使用技能 `$git-commit` 提交已有变更，再结束会话或删除任务文件；测试失败、验证未完成或任务阻塞不免除提交要求，提交说明中如实注明未完成项及验证情况。仅暂存本任务变更，排除其他任务或工作区中的无关变更。若没有实际变更，或只有编号任务文件自身的状态更新或删除，不创建空提交或任务文件专用提交。提交失败时保留任务文件并记录失败证据，不宣称已提交。
- 验证证据在最终回复中报告后，立刻删除该任务 `.md` 文件；不要修改 `plan.md`，不要记录其他东西，避免产生大量垃圾干扰其他任务。

## 何时停下并寻求帮助

只有以下情况在查证和合理排障后仍无法解决，才暂停受影响的操作并寻求帮助：

- 缺失的信息会实质改变用户目标、关键验收标准或授权边界，且无法从现有上下文得出可靠结论。
- 下一步确需新增授权，或工具、权限限制使所有合规可行路径均无法继续。
- 必要依赖或验证条件无法恢复，也无适当替代路径，需要用户提供外部信息或改变环境。

提问前先完成可独立推进的工作，在对应任务文件中记录具体阻塞、错误证据、已尝试方案和所需的最少输入，再集中提出必要问题。不得仅因首次失败、可修复的依赖缺失、常规设计选择或用户暂未回复就停止全部工作；也不得把用户未回复当作批准。

## 何时回溯到前面的步骤

**以下情况返回审查流程：**
- 伙伴根据你的反馈更新了计划
- 基本方法需要重新思考

审查和调整可在已有目标与授权内自主完成，不自动形成用户确认检查点；只有触发上述求助条件时才提问。
