## 确定用途和位置

1. 从用户给出的真实场景提炼技能的触发条件、应完成的工作和可核对的交付。若请求是更新技能，先阅读现有 `SKILL.md`、关联资源和调用方，仅修改本次需要的内容。
2. 用户指定了目录就使用该目录。为当前项目新建技能时，默认放在 `<project>/.shiju-harness/skills/<技能名>/`。改动随包提供的技能时，编辑其源码，并按目标仓库约定接入内置清单。
3. 目录名和 frontmatter 的 `name` 保持一致，使用小写字母、数字和连字符，最长 64 个字符。描述写明技能做什么、什么时候用，使用用户在真实请求里会用到的词。

## 编写内容

以 `SKILL.md` 为入口，例如：

```markdown
---
name: review-api-contract
description: 审查 API 契约变更，识别受影响的调用者并报告需要兼容处理的字段。
---

# 审查 API 契约

读取变更的接口定义和调用方。按字段列出变更、影响范围及验证证据。
```

- 正文只保留会影响执行决策的说明。根据任务风险选择详细程度，固定流程应有明确的正确性或安全理由。
- 复杂的规范、示例和分支流程放进 `references/`。在正文说明何时读哪一份。可重复且容易出错的步骤可用 `scripts/` 辅助。交付物模板放进 `assets/`。
- 正文中的相对路径以技能目录为基准。只引入实际使用的资源，说明脚本依赖和输入。沿用项目现有工具和验证入口。
- 保留已有的权限与操作边界。创建技能本身不授权发送消息、发布、安装依赖或修改无关配置。

## 验证交付

- 检查 YAML frontmatter、目录名、触发描述和相对资源链接。用一个应命中、一个不应命中的实际示例审查范围。
- 通过目标项目的技能列表确认路径和元信息。需要审计时，从项目根目录运行 `shiju skills audit <技能目录>`。验证脚本时使用安全示例和项目允许的验证方式。
- 反馈保存路径、可用范围和实际验证结果。
