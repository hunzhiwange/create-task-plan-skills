# 编写计划

使用此技能将规格说明或粗略请求转化为实施计划，使另一个代理能够在聚焦会话中安全执行。

开始时请说：`我正在使用 create-task-plans 技能来创建实施计划。`

## 验证范围

- 所有任务的日常开发和单任务验收禁止默认运行全量测试；必要的定向单元测试在本任务内完成，覆盖本次修改及直接受影响行为，优先复用现有测试，不积压到最终回归。
- 不将全量构建、全仓 lint 或格式检查作为每个子任务的固定步骤。公共检查在统一回归按需合并执行；全量测试只有用户明确要求或项目明确的统一回归流程要求时才运行，不因进入回归就自动扩大范围。
- 定向测试通过后按任务完成规则收尾；未执行或失败的检查如实记录，不宣称通过。统一回归补跨任务集成及必要公共检查，不机械重跑未受后续改动影响的已通过单元测试。
- Rust 任务另按 Rust 项目约定控制编译内存；不将 Rust 编译资源限制套用到其它语言的普通单元测试。

## 无人值守与自主决策

默认按无人值守流程工作，不假设用户在旁等待回答。用户提出目标后，授权范围内的常规、可逆、低风险决策由代理自行选择最佳可行路径，不逐项请求确认，也不在阶段结束时询问是否继续。

- 先查阅仓库、现有约定、工具结果和已给出的上下文。实现细节、命名、任务拆分、验证方式等存在多种合理选择时，优先选择符合现有模式、改动小、易验证的方案，并在计划中简要记录选择依据。
- 对不影响核心目标和验收标准的缺失细节，采用有依据的默认值，并明确标为假设；不要把假设写成已确认事实。只有会实质改变用户目标、关键验收标准或授权边界且无法从上下文解决的歧义，才需要澄清。
- 缺少依赖、工具报错、格式问题或来源产物不完整时，先在授权范围内调查、修复或选择等效路径；能独立推进的部分继续完成。无法解决的部分记录具体阻塞、已尝试路径和所需输入，不因一个局部问题停止整个计划。
- 不把无人值守视为新增授权。涉及未授权的破坏性操作、对外发布或不可逆变更时，先完成可安全准备和验证的部分，再集中提出必要问题；不得把用户未回复当作批准，也不得绕过权限或工具限制。
- 将上述自主决策原则提炼到 `plan.md` 的“公共执行约定”中，由每个编号任务引用，使独立执行会话无需依赖入口提示词也能遵守。

## 输出位置

将每个计划保存为一个目录：

```text
./.plans/YYYY-MM-DD-<功能名称>/
├── plan.md
├── prompt.md
├── 1-<first-task>.md
├── 2-<second-task>.md
└── ...
```

- `YYYY-MM-DD` 使用当前日期。
- 所有计划全部使用中文。
- 使用简短的中文短横线分隔功能标识。
- 如果用户提供了不同路径，则使用用户指定的路径。
- 将 `plan.md` 保持为整体架构和公共执行规则的参考指南；生成后只读，后续提示词不得要求修改或清理它。
- 将 `prompt.md` 保持为所有任务的执行入口列表，方便用户复制粘贴到不同对话框；公共要求归入 `plan.md`，任务专属要求归入编号任务文件。
- 将实现细节放入编号任务文件中，不要写进一个过大的计划文件。

## 计划工作流

1. 在编写计划前，先阅读请求、相关仓库说明、现有模块、工厂连线和相邻测试。
2. 如果请求涉及外部规格、变更提案、设计文档、能力说明或任务清单，先用对应工具或清单确认活跃变更；名称明确时直接使用，否则根据用户目标和上下文选择匹配的活跃变更；仅多个候选会导致实质不同的范围且无法查证时让用户选择。
3. 对外部变更，先读取其状态，并以工具返回的模式、产物、依赖关系和实现指令为准；不要猜测固定文件名或固定流程。
4. 读取工具返回的依赖文件、上下文文件和其它必要仓库上下文后，再编写计划。
5. 如果目标、成功标准、非目标、设计边界、变更状态或产物依赖不清楚，先查证并按“无人值守与自主决策”处理；对可合理推断的细节记录假设，仅对无法消除的关键歧义澄清。
6. 对仍有多个可行路线的设计，记录 2-3 个方案的主要权衡和最终选择。
7. 定义范围边界。如果请求横跨独立子系统，将其拆分为单独的计划目录，或清晰标记范围外工作。
8. 围绕一个可测试行为、一个窄模块变更或一个未完成来源任务来划分任务边界，确保一个代理通常能在一个聚焦会话中完成。
9. 对会改变行为的代码，定义实现前必须先编写的失败测试。
10. 定义每个任务被标记为 `已完成` 前需要哪些新证据；如果任务映射外部任务清单，说明完成后需要按来源工具规则更新对应任务状态。
11. 在具体的任务和 prompt.md 同时写出线性执行顺序和可并行执行批次；并行批次只包含没有相互依赖、不会争用同一文件或验证资源的任务。
12. 先编写包含全局架构的 `plan.md`，再编写每个编号任务文件，最后编写 `prompt.md`。
13. 将公共的执行技能、自主决策、验证范围、阻塞处理、提交和清理规则集中写入 `plan.md`；每个任务引用它并声明自身依赖、具体命令和验收证据。`prompt.md` 的标题展示批次及依赖，代码块只保留“执行 `<任务文件路径>`。”。
14. 重新通读完整计划，检查缺失需求、占位符、不安全假设、任务顺序、并行批次冲突和 `prompt.md` 是否覆盖每个任务。
15. 特别注意，并行批次一定保证正确，不要将不能并行的放到同一个批次，不能并行就升高批次数。

除非用户明确要求同时进行计划和实现，否则编写计划时不要实现代码。

## 项目构建与验证能力

当前任务涉及 Rust/Cargo 构建或验证时，读取 [Rust 项目约定](references/rust.md)，直接使用原生 Cargo 命令；其它任务不加载该参考。按该参考覆盖默认会话调度，并将其中的编译内存约束、取消与进程收尾、定向测试及公共检查边界集中写入 `plan.md` 的 Rust 专用规则小节，注明仅适用于 Rust/Cargo 任务，避免生成并行重编大型测试目标的计划。

先读取目标仓库的协议、项目清单、构建配置、现有脚本和 CI，识别本任务实际涉及的语言与工具链；混合项目按受影响部分分别选择验证路径。不要默认项目使用某种语言、包管理器、解释器或加速工具，也不要假定仓库提供某个脚本、别名、缓存目录或资源池。

- 有仓库专用的开发、缓存、并发或资源管理约定时，在 `plan.md` 中集中写明这些约定及适用范围，由相关任务引用，并核对所需工具、文件、调用格式和目标确实存在。没有相应入口时使用项目已有的原生命令，不为普通业务任务引入加速工具或另建基础设施。
- 生成可直接执行的具体命令及其运行目录、必要环境、目标与成功信号；不要留给执行者或用户补配置。纯文档或无需构建的任务采用风险匹配的轻量检查。
- Rust 开发验证直接使用原生 Cargo 定向命令，复用 Cargo 自身增量缓存；不生成包装脚本、加速器探针或常驻测试入口要求。其它语言按自身现有工具运行必要定向测试。
- 已有缓存和资源生命周期约定时，在同一阶段复用，避免重复初始化或无依据地清缓存。并发执行遵守项目的源码、产物、机器资源与外部服务约束，不能将一个仓库的目录、并发数量或线程参数推广到所有项目。
- 每次修改后需要新的验证结果，实际运行数量及失败/通过情况符合预期；旧结果、零测试或仅构建成功不能替代行为验收。变更超出快反馈工具的适用边界时，按项目约定重启或回到原生路径。最终强制检查、真实渲染及实机验收仍按仓库要求执行。

公共构建、资源和验证约束集中写入 `plan.md`，注明适用语言或任务范围；具体目标、命令和成功信号留在对应任务文件。任务通过引用继承公共要求，不复制相同规则；`plan.md` 生成后只读，`prompt.md` 只负责定位任务。不把某个仓库的专用命令写进通用模板。

## `plan.md` 模板

```markdown
# <功能名称> 计划

目标：<用一句话描述结果，不超过 100 字>

范围：<包含哪些内容，不超过 300 字>

范围外：<有意排除哪些内容，不超过 100 字>

假设：<仅写有仓库上下文支持的具体假设，不超过 200 字>

## 设计决策 <不超过 100 字>

- <自主选择的方案及依据、关键权衡或用户已明确的约束>
- <如适用，记录来源变更、模式、关键产物和已确认约束>

## 架构说明 <不超过 100 字>

- <需要遵循的关键现有模块/模式>
- <重要约束、风险或安全边界>

## 开发策略

- 对会改变行为的代码，使用失败验证-通过验证-重构。
- 在实施步骤前规划失败验证命令和预期失败。
- 将实施步骤限制在失败测试所证明的行为范围内。
- 测试真实行为，不验证模拟对象或实现细节。

## 公共执行约定

- 每个任务开始前读取本计划及任务文件，确认任务声明的批次和依赖条件已满足。本文件保存整体架构和公共规则，生成后只读，不修改、清理或记录进度。
- 使用执行技能 `<实际可用的 do-task-plans 技能名称或路径>`；该入口在生成计划时核实并填写，不在每个任务或提示词中重复。
- 按无人值守方式执行：常规、可逆、低风险事项自行选择符合仓库约定的最佳可行方案；记录影响后续执行的假设、决策及依据，不重复请求已有授权。仅在关键歧义无法消除或确需新增授权时集中询问，不将用户未回复视为批准。
- 按本任务的实现和验证计划推进；遇到问题先调查根因，在已有授权内修复完成原目标所必需的相邻依赖或采用等效路径，记录调整依据，不扩展无关功能或削弱验收标准。局部受阻时继续不受影响的工作。
- 仅在对应编号任务文件中记录状态、阻塞原因、错误证据、已尝试路径和待运行检查；完成证据在最终回复中报告。状态和文件清理按下方“公共收尾规则”处理。

## 公共验证与资源规则

- 必要定向单元测试在各任务内完成，覆盖本次修改及直接受影响行为；禁止默认逐任务全量测试或整仓检查。
- 统一回归补跨任务集成及必要公共检查，同一公共命令合并执行一次；不机械重跑未受后续改动影响的已通过测试。全量测试仅在用户明确要求或项目统一回归流程明确要求时运行。
- <按仓库事实填写共用的运行目录、环境和资源生命周期；语言专用规则单列小节并注明适用范围。具体测试目标、命令和成功信号写入各任务，不复制到此处>

## 公共收尾规则

- 仅使用状态：`未开始`、`已完成`、`已阻塞`、`待回归`。
- 获得本任务要求的当前验证证据后，标记为 `已完成`，在最终回复中报告完成证据并删除对应编号任务文件。
- 合理排障和替代路径仍无法解除阻塞时，标记为 `已阻塞`，保留对应编号任务文件并记录具体原因、已尝试路径、已运行及未完成的检查和所需输入，不声称完成。
- 实现已完成，仅因与本次修改无关的原因无法完成验证时，可标记为 `待回归`；保留对应编号任务文件，记录已获证据、未通过或未运行的检查及后续回归命令，不伪造通过结果。回归通过后按 `已完成` 收尾。
- 无论以 `已完成`、`待回归` 还是 `已阻塞` 结束任务，只要有本任务实际代码、测试、配置或文档变更，都必须先使用技能 `$git-commit` 提交已有变更，再结束会话或删除任务文件；测试失败、验证未完成或任务阻塞不免除提交要求，提交说明中如实注明未完成项及验证情况。仅暂存本任务变更，排除其他任务或工作区中的无关变更。若没有实际变更，或只有编号任务文件自身的状态更新或删除，不创建空提交或任务文件专用提交。提交失败时保留任务文件并记录失败证据，不宣称已提交。

```

## `prompt.md` 模板

`prompt.md` 只负责定位任务和展示执行顺序，不是执行契约或进度来源。它必须覆盖所有编号任务，并保持与任务文件一一对应。每个代码块只写“执行 `<任务文件路径>`。”；公共要求写入 `plan.md`，专属要求写入对应任务文件，不在总说明或代码块中重复。

````markdown
# <功能名称> 任务提示词

按批次顺序执行；同批次任务可并行。复制对应提示到独立对话框。

# 批次 1

## 任务 1: <任务名称>【批次 1】 依赖：无

```text
执行 `<plan-dir>/1-<first-task>.md`。
```

# 批次 2

## 任务 2: <任务名称>【批次 2】 依赖：批次 1

```text
执行 `<plan-dir>/2-<second-task>.md`。
```
````

- 每个提示只包含具体任务文件路径和“执行”指令；执行技能在 `plan.md` 中指定。
- 按批次、任务编号列出，标题中的批次和依赖与编号任务文件一致。
- 无人值守、构建与资源、验证、提交、状态更新和文件清理等公共要求均放入 `plan.md`，由编号任务引用，不向提示词追加规则或提醒。

## 任务文件模板

每个任务只需引用同目录的 `plan.md` 并声明自身差异。执行者从任务文件进入，先读取引用的公共规则，再按本任务依赖、目标和验收实施，无需阅读 `prompt.md` 或所有其他任务。公共规则维护一份，不复制到各任务，也不以“同上一任务”代替引用。

```markdown
# 任务 N: <任务名称>

先阅读并遵守 [公共执行规则](plan.md)，再执行本任务。

批次：【批次 3】 <依赖批次 1,2或“无”>

状态：未开始

目的：<此任务要完成什么，不超过 100 字>

来源任务：<对应来源任务编号或“无”>

预计会话范围：<为什么这适合一个聚焦会话，不超过 300 字>

## 文件

- 新建：`<实际新增文件路径>`
- 修改：`<实际修改文件路径>`
- 测试：`<实际测试文件路径>`

## 上下文

- <实现者必须了解的现有符号、模式、命令或约束，不超过 200 字>

## 专属约束（适用时）

<仅写本任务与公共规则不同的具体约束及依据；没有差异时省略>

## 测试计划

- 行为：<此任务证明的单一行为或缺陷>
- 失败验证测试：<要新增或修改的测试文件和测试名>
- 失败验证命令：`<确切命令>`
- 预期失败原因：<实现前的具体失败原因>
- 通过验证命令：`<确切命令>`
- 开发验证：<原生定向命令与成功信号；Rust 直接调用 Cargo>
- 任务内验收：<必要定向单元测试及受影响目标检查，不填全量命令>
- 统一回归：<跨任务集成及必要公共检查；重复命令只执行一次>
- 模拟策略：<优先使用真实依赖，或说明要模拟的确切边界及原因>

## 步骤

<只写本任务具体的实施动作、符号及接线顺序；通用的失败验证-实现-通过验证流程继承 plan.md，不重复列出>

## 验证

- 运行：`<限定包、测试目标及相关行为的确切命令；禁止默认全量测试>`
- 预期：<具体成功信号>
- 所需证据：<失败验证的预期失败、通过验证成功、退出码、输出行、失败数量、已审查差异或证明完成的清单结果>


```

对于代码变更，包含确切文件路径、相关符号、预期行为和聚焦验证命令。只有在能消除歧义时才包含代码片段；避免粘贴会随仓库漂移的大段代码。如果测试驱动开发不适用，在任务中说明原因，并将测试驱动开发计划小节替换为适合仓库的验证计划。

## 任务大小规则

如果一个任务符合以下情况，就说明它过大：

- 触及多个无关模块。
- 需要多个独立设计决策。
- 有超过一个主要验证故事。
- 很可能超出一个聚焦编码会话。
- 混合了功能工作、重构工作和基础设施工作。

当任务过大时，按行为、模块边界或验证目标拆分为多个独立的任务。保持任务文件的依赖关系显式。

## 质量门槛

- 遵守仓库说明和禁用命令。
- 计划前先收敛目标、成功标准、非目标和设计边界；不清楚时先查证，对常规细节自主选择，仅对无法解决的关键歧义澄清。
- 对外部规格或变更相关计划，以来源工具返回的变更、模式、产物、依赖关系、指令和上下文文件为准。
- 不把来源工具的上下文或规则原样复制进计划，只提炼与实施相关的约束。
- 若来源工具返回阻塞状态或缺少必要产物，先按其规则尝试解决，继续规划不受影响的任务；确实无法解决时记录阻塞，不伪造可执行计划。实质范围变化或未授权风险按“无人值守与自主决策”处理。
- 常规设计决策和为原目标补充的必要任务直接记录在本次计划中，不以询问是否回写来源产物阻断流程。来源产物仅在已有授权和来源规则允许时更新；未获授权时保留建议回写内容，继续本次计划。
- 如果遇到格式化校验，看看是否存在格式化工具，先自动化格式一下，然后才校验。
- 优先使用现有模式，而不是新增抽象。
- 不要添加推测性的配置、特征、特性开关或扩展点。
- 保持不支持路径显式。
- 在相关时包含安全和权限边界。
- 每个 `已完成` 状态都必须依赖当前验证证据，而不是信心或过去的运行结果。
- 对行为变更，要求失败验证和通过验证证据，除非任务明确说明测试驱动开发不适用的原因。
- 优先使用真实行为测试；只 mock 清晰的外部、缓慢、不安全或非确定性边界，并说明 mock 的副作用和数据形状。
- `plan.md` 集中定义公共执行和收尾规则，明确 `已完成`、`待回归`、`已阻塞` 三种收尾状态有实际变更时均须先使用 `$git-commit` 提交；只有本任务文件自身的状态更新或删除时不提交，排除其他任务或工作区中的无关变更。
- 除非用户明确要求兼容旧的逻辑和迁移旧的数据结构，否则不要在任务中要求兼容或者迁移旧的数据结构。
- 不要写 `TBD`、`TODO`、`later`、`add proper error handling` 或 `similar to previous task` 这类占位符。
- 不要引用计划尚未定义或验证的类型、函数、文件或命令。

## 自我审查

完成前：

- 检查每个用户需求是否映射到至少一个任务。
- 检查每个任务是否能在其依赖完成后独立执行。
- 检查 `prompt.md` 是否存在，覆盖每个任务，批次和依赖与任务文件一致，且每个可复制代码块只有“执行”及任务路径这一句入口。
- 检查 `plan.md` 是否包含具体任务步骤、状态或进度信息；如果包含，立刻移入对应编号任务文件，`plan.md` 只保留整体架构和公共规则。
- 检查并行批次中的任务没有任务依赖、文件写入或验证资源冲突。
- 检查所有验证命令是否遵守仓库说明。
- 检查每个任务的语言、工具、脚本、开发快反馈和完成验收命令是否来自目标仓库事实；资源与缓存约定按该项目落实，不假定任何专用加速器、解释器或槽位池存在。
- 检查每个任务是否定义了被标记为 `已完成` 前所需的证据。
- 检查会改变行为的任务是否定义了失败验证和通过验证命令。
- 检查不存在占位符或含糊步骤。
- 检查相同执行段落未重复写入多个任务；公共规则只在 `plan.md` 维护，语言专用规则有清晰适用范围。
- 脱离 `prompt.md` 逐个审查编号任务文件：是否能通过明确的 `plan.md` 引用获取公共执行和收尾规则，并从任务本身确定批次依赖、实现差异、具体命令和验收证据；不得要求执行者另读入口提示词才能补齐执行要求。
- 检查自主执行原则已写入 `plan.md`，且每个任务均引用它，且没有要求对常规小问题逐项授权或立即停下提问的冲突指令。
